# Optional Jetson NVDEC decoding

`main.py encode --ff_hwaccel jetson` requests NVIDIA hardware decoding for supported local 8-bit H.264 MP4/MOV files. The existing command's other arguments remain necessary. The default is still `none`.

The backend uses GStreamer `nvv4l2decoder`, transfers I420 pixels without resizing, and carries timestamps through raw Matroska on a dedicated descriptor. FFmpeg restores the source time base before applying the existing CPU scale/color/FPS filters. Diagnostic stdout is isolated from video data.

Unsupported inputs and detected hardware failures retry the entire video in software. Empty output, partial planes, nonzero subprocess exits, and NVIDIA allocation errors prevent a hardware attempt from committing its bitstream. Decoder failures also prevent the software path from committing partial output.

The current validated scope excludes MKV/WebM, other codecs, 10-bit/full-range/interlaced video, multiple video streams, video side data, different container/video start times, and widths not divisible by eight or odd heights. These inputs use software automatically. Matroska source packet-duration rounding changed the final selected frame in testing, so it is explicitly excluded rather than silently changing output.

## Validation on Jetson Orin Nano Super, L4T 36.4.7

Tests used generated videos only, with the existing three production workers left running.

- 1920x1080 H.264 MP4, 96 frames: software and hardware produced identical 176x96 YUV420 frames after the production 24 FPS filter. SHA-256: `03ae71f1eb676a75eb81395aea1469cdd8b80bf3b9380b097748e85ef33ffd94`.
- 640x360 H.264 MP4 with B frames, 96 frames: identical filtered pixels. SHA-256: `eff666ee372de116236b4ff4ce79e13904df38c970ef767e38a295f40123c4c8`.
- Variable-frame-rate H.264 MP4: identical 83 filtered frames. SHA-256: `0861a2dd9ea243ed354e9fa1ab5c2dad2598a00c099c30610b380d339590461a`.
- NVIDIA's FFmpeg `h264_nvv4l2dec` lost frames, changed pixels, and wrote diagnostics to stdout; it is not used.
- The GStreamer bridge was slower in these short decode-only tests (about 0.97–1.92 seconds versus 0.27–0.46 seconds for software, including startup/probing). This is not an end-to-end neural throughput measurement.
- A single additional neural benchmark failed during model loading with CUDA out-of-memory/NvMap allocation errors. Full neural bitstream parity and throughput could not be measured under the current production load. Further standalone hardware tests also encountered intermittent allocation errors; those are detected even when both subprocesses return zero.
- Seven unit tests cover decoder failure/timeout, allocation diagnostics, unsupported inputs, Matroska fallback, truncated planes, preserving an existing output after decoder failure, and whole-file software retry.

The production tmux session and its boot command were not restarted or changed. Hardware remains opt-in because full pipeline validation is pending and no speed improvement has been demonstrated. Existing systemd/tmux boot setup remains in place.

## Reproduce with generated fixtures

```bash
mkdir -p benchmarks/optimization_nvdec/fixtures
ffmpeg -n -f lavfi -i testsrc2=size=640x360:rate=24 -frames:v 96 \
  -c:v libx264 -preset veryfast -crf 23 -threads 2 -pix_fmt yuv420p \
  benchmarks/optimization_nvdec/fixtures/test_h264_360.mp4
python benchmarks/check_jetson_pixels.py \
  benchmarks/optimization_nvdec/fixtures/test_h264_360.mp4
python -m unittest discover -s tests -p test_jetson_decode.py -v
```

When enough GPU memory is available, run the single-process neural comparison with a new output directory:

```bash
python benchmarks/benchmark_jetson_decode.py \
  --fixture benchmarks/optimization_nvdec/fixtures/test_h264_360.mp4 \
  --output benchmarks/optimization_nvdec/neural_comparison
```

The benchmark invokes only per-file encoding; it never invokes channel/source cleanup. Generated media, models, compiled extensions, and benchmark outputs are excluded from Git.
